# 自动划词误触发审查（待确认，尚未修改运行行为）

## 原因与证据

用户实测：保存文件时默认文件名被系统选中，TranslateMe 自动弹出译文。

当前 `watch_selection` 每 350 ms 读取前台焦点控件，选中文字至少 2 个字符、身份稳定 700 ms 且没有正在处理的任务就触发。它不检查控件用途、输入意图、鼠标按下状态或选区变化的来源，也没有“切换应用后先记录旧选区”的基线。

原生返回的 `editable` 没有参与自动触发判断。macOS 现有字段服务于回填流程，其判定包含“选区范围是否可设置”；可选择的只读文本也可能满足这一条件，不能直接把 `editable == true` 等同于正在编辑。

固定样例实验直接调用生产 `Document::parse`，不读取窗口、不访问翻译服务。输出保存在忽略目录 `artifacts/trigger-audit.txt`。`Untitled`、`report.pdf`、搜索词和 `git status` 都会产生待翻译片段；纯 URL、路径、数字、`main.ts` 和 `user_id` 虽没有待翻译片段，现有阅读流程仍发布原文结果并显示浮窗。

除用户报告的保存框外，下表是按代码推断的风险，尚未逐个做目标应用实测。前提都是目标应用向系统暴露了对应的文本选区。

## 场景与建议

| 场景 | 容易误触发的原因 | 建议默认行为 |
| --- | --- | --- |
| 保存/另存为的文件名、文件重命名 | 系统为方便输入自动全选 | 不自动翻译 |
| 浏览器地址栏、打开路径、搜索/查找替换、命令面板 | 聚焦或快捷键会全选当前值 | 不自动翻译 |
| 聊天输入框、代码编辑器、表单输入 | 为复制、删除、替换而选择文字 | 不自动翻译；保留明确的翻译快捷键 |
| 数字、路径、URL、明确的标识符和围栏代码 | 无须翻译但仍进入浮窗发布流程 | 不调用引擎、不弹原文框 |
| 切回应用、窗口重新打开、程序恢复旧选区 | 既有选区被当作新的翻译请求 | 建立焦点基线，等待新的主动选词 |
| 拖选时按住鼠标停顿 | 选区已经稳定，但选择动作还未结束 | 松开后再开始稳定等待 |
| 程序自动补全、自动选中搜索结果 | 文本变化未必来自阅读动作 | 没有新的选词动作时不自动触发 |
| 普通只读正文中的拖选、双击选词 | 明确的阅读选区 | 自动显示译文 |

密码与系统标记的受保护字段已有拒绝读取规则，继续保留。明确的手动阅读、写入快捷键与自动划词分开处理；自动忽略不能变成所有翻译入口均不可用。

“所有编辑区域默认不自动”的取舍：在 Word 可编辑正文或代码编辑器里阅读选中文字，也需要主动按阅读快捷键。不能把只读正文的“可选中”误判为“可编辑”。对于无法可靠确定上下文的控件，先不自动弹出，手动入口继续可用。

## 最小实现边界与验收

需要原生层报告可靠的控件类别、窗口/控件身份及选词动作状态，再由共享触发逻辑统一决定是否自动启动。仅观察鼠标按下/松开等动作元数据，不采集键盘输入内容，不增加截图或 OCR。能力不足的平台应明确降级，不假称可以完全判断用户意图。

共享层在调用引擎和展示“正在翻译”之前执行过滤；焦点变化、进入忽略区域以及已失效的选区应同时取消旧结果的显示资格。手动请求仍跟踪选区位置，但不被自动触发过滤误取消。内容过滤先用已有的确定性保护规则，不能仅凭英文长度、文件扩展名或等宽字体屏蔽整段正文；渲染后丢失代码边界的问题仍按既有结构化选词方案单独处理。

涉及 macOS / Windows 原生取词结果和共享监听逻辑的协同修改。按用户提供的 AGENTS.md 第 2 条，确认策略后再实施；本次仅提交审查文档，未重新构建或重启应用。

验收至少包括保存框、重命名、地址栏、搜索框、聊天输入、只读正文、双击选词、拖选中停顿、切回旧选区、纯路径/数字，以及自动忽略时两种手动快捷键和已有浮窗跟随仍正常。macOS 实测与 Windows 编译/实机结果分别记录。
