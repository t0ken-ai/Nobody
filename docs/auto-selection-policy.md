# 自动划词白名单与误触发过滤

## 用户确认的范围

用户最新确认默认应用是 **ChatGPT Desktop、Claude Desktop**，并允许从本机选择更多应用。白名单只限制自动触发，工作台和明确按下的手动翻译快捷键保持现有行为。

macOS 默认按 Bundle ID `com.openai.chat`、`com.anthropic.claudefordesktop` 匹配。当前机器 `/Applications/ChatGPT.app` 实际为 `com.lencx.chatgpt`，`/Applications/Codex.app` 为 `com.openai.codex`，不会因同名或内部 CFBundleName 被误归为默认 ChatGPT 客户端；用户可手动选入。默认客户端尚未安装时保留该默认项，界面显示未安装。

自选 macOS 应用通过原生 NSOpenPanel 添加，每次默认打开 `/Applications`，允许多选 `.app` 并浏览其他本机目录。解析别名/符号链接、检查本机卷和可执行应用包，保存规范化路径与 Bundle ID，不启动应用、不读取其文档。运行时两者必须同时一致，移动后需重新添加。Windows 使用原生文件对话框选择 `.exe`，初始目录为 Program Files；自选项按规范化完整路径匹配，排除网络路径。Windows 默认项使用 `ChatGPT.exe` / `Claude.exe` 名称身份，尚未做实际客户端身份/行为验收，不宣称已验证发布者签名。

添加、移除、恢复默认先修改表单草稿，保存才生效；取消选择器不改变列表，重复选择同一应用不会重复添加。选择器不受翻译请求的超时限制，也不阻塞选区监听工作线程。保存前再次检查本机文件身份，拒绝无效或已被替换的路径。前端通过文本节点显示应用名和路径，避免文件名成为 HTML。

旧 `automaticApps: ["codex", "claude"]` 迁移为 `["chatgpt", "claude"]`，显式空列表和单项移除保留；新手动加入的 Codex 是路径对象，不会被迁移。均不按窗口标题或网页域名匹配，也不默认将终端加入白名单。

## 修复前的原因与证据

用户实测：保存文件时默认文件名被系统选中，TranslateMe 自动弹出译文。

修复前 `watch_selection` 每 350 ms 读取前台焦点控件，选中文字至少 2 个字符、身份稳定 700 ms 且没有正在处理的任务就触发。它不检查控件用途、输入意图、鼠标按下状态或选区变化的来源，也没有“切换应用后先记录旧选区”的基线。

修复前原生返回的 `editable` 没有参与自动触发判断。macOS 现有字段服务于回填流程，其判定包含“选区范围是否可设置”；可选择的只读文本也可能满足这一条件，不能直接把 `editable == true` 等同于正在编辑。

固定样例实验直接调用生产 `Document::parse`，不读取窗口、不访问翻译服务。输出保存在忽略目录 `artifacts/trigger-audit.txt`。`Untitled`、`report.pdf`、搜索词和 `git status` 都会产生待翻译片段；纯 URL、路径、数字、`main.ts` 和 `user_id` 虽没有待翻译片段，修复前阅读流程仍发布原文结果并显示浮窗。

除用户报告的保存框外，下表是按代码推断的风险，尚未逐个做目标应用实测。前提都是目标应用向系统暴露了对应的文本选区。

## 自动触发规则

| 场景 | 容易误触发的原因 | 当前默认策略 |
| --- | --- | --- |
| 保存/另存为的文件名、文件重命名 | 系统为方便输入自动全选 | 不自动翻译 |
| 浏览器地址栏、打开路径、搜索/查找替换、命令面板 | 聚焦或快捷键会全选当前值 | 不自动翻译 |
| 聊天输入框、代码编辑器、表单输入 | 为复制、删除、替换而选择文字 | 不自动翻译；保留明确的翻译快捷键 |
| 数字、路径、URL、明确的标识符和围栏代码 | 无须翻译但仍进入浮窗发布流程 | 不调用引擎、不弹原文框 |
| 切回应用、窗口重新打开、程序恢复旧选区 | 既有选区被当作新的翻译请求 | 建立焦点基线，等待新的主动选词 |
| 拖选时按住鼠标停顿 | 选区已经稳定，但选择动作还未结束 | 松开后再开始稳定等待 |
| 程序自动补全、自动选中搜索结果 | 文本变化未必来自阅读动作 | 没有新的选词动作时不自动触发 |
| 普通只读正文中的拖选、双击选词 | 明确的阅读选区 | 自动显示译文 |

密码与系统标记的受保护字段已有拒绝读取规则，继续保留。明确的手动阅读、写入快捷键与自动划词分开处理；自动忽略不能变成所有翻译入口均不可用。

“所有编辑区域默认不自动”的取舍：在 Word 可编辑正文或代码编辑器里阅读选中文字，也需要主动按阅读快捷键。不能把只读正文的“可选中”误判为“可编辑”。对于无法可靠确定上下文的控件，先不自动弹出，手动入口继续可用。

## 实现边界与验收

原生层先检查白名单；非白名单的新自动请求在读取选中文字前返回。允许的应用再检查焦点控件及祖先的可编辑、对话框和阅读区域语义，报告上下文身份。`selection.rs` 集中处理触发规则，只有最近完成的鼠标拖选或双击选词才开始 700 ms 稳定等待；已消费的动作不会因切回旧选区再次触发。

macOS 使用 NSEvent 鼠标事件，Windows 在原有 COM 工作线程中间隔约 16 ms 采样左键状态和坐标。仅在内存保存允许应用的动作元数据，不监听键盘输入内容，不增加截图或 OCR。Windows 遇到很短的点击或慢 UIA 调用可能漏掉动作，此时不自动弹窗，可使用手动快捷键。自动模式不监听纯键盘选词。

共享层在调用引擎和展示“正在翻译”之前执行过滤；焦点变化、进入忽略区域以及已失效的选区应同时取消旧结果的显示资格。手动请求仍跟踪选区位置，但不被自动触发过滤误取消。内容过滤先用已有的确定性保护规则，不能仅凭英文长度、文件扩展名或等宽字体屏蔽整段正文；渲染后丢失代码边界的问题仍按既有结构化选词方案单独处理。

用户明确白名单后已实施原生取词、共享监听、配置和设置界面的协同修改。手动结果只允许跟踪原 PID 和原控件，不能借此扩大自动白名单；设置改变或源选区失效会取消旧结果的显示资格。

限制：系统暴露的焦点和控件语义可能不完整，无法可靠判断时不自动弹出。鼠标动作、选区变化与程序自动修改之间没有所有应用通用的因果证明，不能保证覆盖一切自定义控件。渲染后代码边界丢失的问题没有在本次顺带解决。

此前固定双应用版本的 19 个 Rust 测试通过，覆盖配置迁移/空白名单、鼠标动作消费、编辑/忽略上下文、拖选中等待、焦点切换、旧动作、忙碌任务、内容过滤，以及手动来源跟踪和已有浮窗行为。该版 macOS 应用界面已验证两个默认勾选项，以及取消 Claude Desktop 后保存、再恢复并保存。TypeScript 与生产前端构建、Swift 编译、Windows 适配模块交叉编译均通过。

真实应用仍需验收保存框、重命名、搜索框、聊天输入、只读正文、双击选词、拖选中停顿、切回旧选区，以及手动快捷键和浮窗跟随。规则单元测试与真实应用端到端结果分别记录在 `verification.md`，不将单元测试冒充目标应用实测。
